вопросах. Написан обычным языком: где нужен термин — он тут же объяснён одной фразой. Каждый факт
взят из кода, теста или отчёта с цифрами, а не из памяти.

  чтобы начать разговор.
- **Разделы 2–13** — по одной подсистеме: что делает, как устроено, почему именно так, где подвох и
  чем проверено. Сюда смотришь, когда копают глубже.
- **Раздел 14** — нагрузочные эксперименты и реальные цифры.
- **Раздел 15** — что честно не сделано (чтобы не блефовать на «а что бы улучшил»).
- **Раздел 16** — каверзные вопросы и короткие ответы.
- **Раздел 17** — шпаргалка с числами.

## 0. Питч на 30 секунд

Это сервис коротких ссылок с аналитикой переходов. Человек регистрируется, создаёт короткую ссылку
на длинный адрес, может задать срок жизни и лимит переходов, потом смотрит статистику: сколько
переходов, по дням, откуда пришли. Сам переход по короткой ссылке — публичный и быстрый, без
регистрации.

Под капотом: Java и Spring Boot, PostgreSQL для данных, Redis для кэша, Kafka для событий переходов,
nginx как единая точка входа, интерфейс на React, Prometheus и Grafana для метрик. Всё поднимается
одной командой в Docker. Два контура CI (GitHub Actions и Jenkins), тесты от юнитов до нагрузки.

Главная фишка, которую стоит сказать сразу: **переход и запись аналитики разведены**. Сервер отдаёт
редирект мгновенно, а строку «был клик» дописывает в базу фоновый обработчик через Kafka. Поэтому
статистика появляется с небольшой задержкой, зато сам переход не тормозит из-за записи.

## 1. Рассказ на две минуты (как идёт запрос)

**Создание ссылки.** Приходит запрос с токеном. Сервер проверяет токен, потом лимит «не больше N
ссылок в минуту на человека», потом валидность адреса и параметров. Дальше берёт следующий номер из
счётчика в базе и превращает его в короткий код (буквы и цифры). Если человек задал свой алиас —
берёт его, проверив, что не занят и не зарезервирован. Вставляет строку в базу и отдаёт короткую
ссылку.

**Переход по ссылке.** Приходит `GET /код` без токена. Сервер сначала смотрит в Redis: если адрес
там есть — сразу отдаёт редирект. Если нет — идёт в базу, достаёт адрес, проверяет, что ссылка жива
(не удалена, не просрочена, лимит не исчерпан), кладёт адрес в кэш и отдаёт редирект. Параллельно
кидает событие «был клик» в Kafka и **не ждёт**, пока его запишут. Фоновый обработчик читает события
из Kafka и дописывает их в таблицу кликов. Статистика считается уже по этой таблице.

**Почему так.** Переходов много, и они должны быть быстрыми. Запись аналитики — работа не срочная,
её можно сделать потом. Поэтому срочное (отдать редирект) и несрочное (записать клик) разнесены:
первое — синхронно и с кэшем, второе — фоном через очередь. Это главное архитектурное решение
проекта, из него растёт почти всё остальное.

Схема целиком: [diagrams/01-context.md](diagrams/01-context.md) и
[diagrams/04-seq-redirect.md](diagrams/04-seq-redirect.md).

## 3. Создание ссылки

**Что делает.** Принимает длинный адрес и необязательные параметры (свой алиас, срок жизни, лимит
переходов), возвращает короткую ссылку.

**Как устроен код ссылки.** Берётся следующий номер из последовательности Postgres (`link_seq`,
старт со 100000) **до вставки**, и кодируется в строку по алфавиту `0-9A-Za-z` (это Base62 — просто
перевод числа в систему счисления с 62 «цифрами»). Номер уникален, значит и код уникален.

- **Почему не хеш от адреса?** Хеш может совпасть для разных адресов (коллизия), и тогда нужен цикл
  «сгенерировал → проверил, не занят ли → повторил», то есть лишний запрос к базе или перехват
  ошибки уникальности при вставке. У номера из счётчика коллизий нет по построению, цикл не нужен.
- **Подвох, который надо признать самому.** Коды идут подряд, их можно перебрать. А переход по коду
  публичный и без лимита. То есть «ссылку знает только тот, кому её дали» держится на том, что адрес
  не угадать, а не на защите. Это осознанный обмен: простота и отсутствие коллизий против
  предсказуемости. Частично лечится алиасом, сроком жизни и лимитом переходов. Случайную часть кода
  и лимит на сам редирект не делал — это в ограничениях (раздел 15).

**Алиас.** Можно задать свой код: буквы, цифры, дефис и подчёркивание, длина 3–32. Занятый — ошибка
409, зарезервированный (`api`, `actuator`, `swagger-ui`, `v3`, `app`, `assets`) — 400. Резерв нужен,
чтобы ссылка не перекрыла служебные маршруты и интерфейс (подробнее в разделе 9).

**Валидация.** Адрес обязателен и не длиннее 2048 символов, схема только http/https и с непустым
хостом. Срок жизни — только в будущем. Лимит переходов — целое не меньше 1. Невалидное — 400 с
разбором по полям.

**Лимит создания.** Не больше 10 ссылок в минуту на пользователя (настраивается). Считается в
памяти процесса через Bucket4j (алгоритм «ведро с токенами»: токены копятся с постоянной скоростью,
каждый запрос тратит один). Кончились — 429 и заголовок `Retry-After`, через сколько можно снова.

- **Подвох.** Лимит в памяти одного процесса: при двух инстансах у каждого свой счётчик, при
  перезапуске обнуляется. Это не защита от распределённого случая, и я это знаю (раздел 15).

**Порядок отказов** (что раньше): нет/битый токен → 401; лимит → 429; валидация → 400; занятый алиас
→ 409; успех → 201.

Чем проверено: юнит-тесты `LinkServiceTest`, интеграционные `LinkIT`, `RateLimitIT`, API-автотесты.
Схема: [diagrams/05-seq-create.md](diagrams/05-seq-create.md).

## 4. Редирект и кэш

**Что делает.** По коду отдаёт редирект на оригинальный адрес. Ответ **302**, а не 301.

- **Почему 302, а не 301?** 301 браузер кэширует навсегда: следующие переходы по этой ссылке уже не
  дошли бы до сервера. Тогда сломались бы и счётчик переходов, и лимит, и срок жизни — сервер бы не
  узнал о повторных кликах. 302 («временно») каждый раз приходит на сервер.

**Путь запроса.** Сначала кэш, потом база:

1. Спросить Redis: есть ли адрес по этому коду?
2. Есть (попадание) — сразу отдать редирект, базу не трогать.
3. Нет (промах) — сходить в базу, проверить, что ссылка жива, положить адрес в кэш, отдать редирект.

Это называется **cache-aside** («кэш сбоку»): приложение само решает, когда читать кэш и когда его
наполнять, а не полагается на автоматическую обёртку.

**Два ключа на ссылку.** `link:код` — сам адрес (что отдать клиенту) и `link-id:код` — номер ссылки
(он нужен для события клика). Читаются одной операцией `MGET` (multi-get, несколько ключей за один
запрос). Время жизни кэша — минимум из «настроенного TTL» и «времени до конца срока ссылки», чтобы
кэш не пережил саму ссылку. При удалении ссылки оба ключа сбрасываются.

- **Почему не `@Cacheable` (готовая аннотация Spring)?** У неё один ключ и один TTL на метод. А тут
  у «адреса для клиента» и «номера для события» разная цена промаха и разное время жизни. Плюс без
  своего класса не было бы выключателя кэша (`APP_CACHE_ENABLED`), на котором построен эксперимент
  «кэш против без кэша» (раздел 14).

**Ссылки с лимитом переходов не кэшируются вообще.** Их доступность зависит от счётчика в базе,
который меняется с каждым кликом. Кэшировать «можно/нельзя» — значит врать между кликами. Поэтому
такие ссылки всегда идут в базу.

**Подвох №1 — лавина промахов (cache stampede).** Когда кэш пустой (холодный старт), все запросы по
одной горячей ссылке разом лезут в базу. Защиты нет — ни блокировки, ни раннего протухания. Это не
оговорка, а измеренное состояние: прогрев холодного кэша на 644 запросах в секунду дал 43,79 %
ошибок у генератора нагрузки и очередь за соединениями с базой (раздел 14, эксперимент 7.6).

**Подвох №2 — устаревание.** Ограничено временем жизни кэша и сбросом при удалении. Другого способа
изменить ссылку в API нет, поэтому сложная инвалидация не нужна.

**Что если Redis упал.** Сервер ловит ошибку, считает её в метрику и отвечает «в кэше нет» — редирект
идёт через базу и остаётся 302. То есть отказ кэша не роняет переходы, а только замедляет их.
Проверено тестами и руками: остановил контейнер Redis — редирект за ~0,43 с, счётчик ошибок вырос,
после возврата Redis попадания снова растут.

Чем проверено: `LinkCacheTest`, `CacheIT` на живом Redis. Схема:
[diagrams/04-seq-redirect.md](diagrams/04-seq-redirect.md).

## 5. Лимит переходов (maxClicks)

**Что делает.** Ссылка может иметь лимит: например, не больше 5 переходов. После исчерпания — 410
Gone («больше нет»).

**Как гарантируется лимит при одновременных запросах.** Не «прочитал счётчик → проверил → записал»,
а один **условный атомарный запрос** к базе:

```sql
UPDATE links SET click_count = click_count + 1
WHERE id = :id AND active
  AND (expires_at IS NULL OR expires_at > now())
  AND (max_clicks IS NULL OR click_count < max_clicks)
```

База обновляет строку, только если все условия выполнены. **Ноль обновлённых строк = лимит исчерпан
прямо сейчас** → 410. Одновременность разруливает сама база на уровне строки, в приложении
блокировок нет.

- **Почему не «прочитал-проверил-записал»?** Между чтением и записью другой запрос успеет сделать то
  же самое, и оба решат «лимит ещё не исчерпан» — получится перерасход. Атомарный запрос эту гонку
  убирает: проверка и увеличение происходят как одно неделимое действие.
- **Чем доказано, что тест ловит именно гонку.** 20 одновременных переходов по ссылке с лимитом 5
  дают ровно 5 ответов 302 и 15 ответов 410, счётчик = 5 (`ConcurrentClickIT`). А если заменить
  атомарный запрос на «прочитал-проверил-записал» (мутация), тест падает: получается 14 ответов 302
  вместо 5. При этом обычные последовательные тесты остаются зелёными — то есть гонку ловит только
  конкурентный тест. Это показано в [test-validation.md](test-validation.md).

**Важная деталь.** Безлимитные ссылки строку в таблице `links` при переходе **не трогают вообще**.
Иначе все клики одной горячей ссылки выстроились бы в очередь на обновление одной строки. Статистика
для них считается по таблице кликов, а не по счётчику в `links`.

Схема жизненного цикла ссылки: [diagrams/07-state-link.md](diagrams/07-state-link.md).

## 6. Клики и аналитика (Kafka)

**Что делает.** Записывает каждый переход в таблицу `click_events`, чтобы потом считать статистику.

**Два пути.** Редирект только **публикует событие** в топик `click-events` и не ждёт записи. Строку в
базу дописывает фоновый обработчик (`click-writer`), который читает топик. Поэтому:

- редирект быстрый — он не делает `INSERT` в базу;
- статистика «догоняет» с задержкой — пока обработчик не дописал, клика в базе нет.

**Почему не записывать клик прямо в запросе.** Замерено: при синхронной записи 95-й перцентиль
времени ответа 117 мс, при асинхронной через Kafka — 9 мс (эксперимент 7.3, раздел 14). То есть
убрали запись из горячего пути — ответ стал в разы быстрее.

- **Что такое перцентиль?** p95 = 9 мс значит: 95 % запросов быстрее 9 мс. Это честнее среднего,
  потому что показывает «хвост» — редкие медленные запросы.

**Подвох — потеря при мёртвой Kafka.** Публикация ограничена по времени (`max.block.ms = 500`): если
брокер недоступен, сервер не висит, а ловит ошибку, считает её в метрику и всё равно отдаёт 302.
Событие при этом теряется навсегда. То есть при мёртвой Kafka переходы работают, а аналитика — нет.
Это осознанный обмен: доступность важнее полноты статистики. Потерь на стенде не наблюдалось, но это
свойство конкретных прогонов, а не гарантия.

- **Тонкость про метрику.** Счётчик ошибок публикации растёт не сразу, а примерно через 2 минуты
  после кликов — срабатывает таймаут доставки в колбэке. Поэтому алерт на эту метрику должен смотреть
  окно ≥ 2 минут, иначе она врёт «всё хорошо».

**Обработчик.** Читает топик в группе `click-writer`, разбирает событие и вставляет строку.
**Дедупликации нет**: если Kafka доставит событие повторно, будет дубль. Ключ сообщения = номер
ссылки, поэтому клики одной ссылки попадают в одну партицию (упорядоченную часть топика) и порядок по
ссылке сохраняется. Топик — 3 партиции, 1 реплика.

**Выключенный обработчик.** Флаг `APP_CLICKS_CONSUMER_ENABLED=false` оставляет сервис работающим, а
события копятся в топике. Включил обратно — обработчик дописал накопленное. Проверено: 10 переходов
→ долг обработчика 10, после включения → 0 и строки дописаны.

**Синхронный режим.** Есть переключатель `app.clicks.mode=sync`: тогда клик пишется в базу прямо в
запросе, без Kafka. Нужен для эксперимента и как запасной вариант. В этом режиме отказ записи не
глотается — переход не состоится, зато клик не потеряется молча.

**Что пишем в клик.** Номер ссылки, время, хеш IP, user-agent, referrer (откуда пришёл).

- **Почему IP хешем, а не открыто?** Приватность: в базе лежит не адрес, а SHA-256 от «адрес + соль».
  Посчитать уникальных посетителей можно, восстановить адрес — нет.

**Статистика.** Считается по сырым событиям: всего переходов, по дням (группировка по дате в UTC),
топ-10 источников. Инкрементальных агрегатов нет — каждый запрос статистики агрегирует сырые строки
на лету. Это узкое место на больших объёмах (раздел 15).

Чем проверено: `ClickEventPublisherTest`, `ClickEventWriterTest`, `StatsIT`, API-автотесты с
ожиданием через Awaitility (аналитика приходит позже ответа). Схема:
[diagrams/06-seq-clicks-async.md](diagrams/06-seq-clicks-async.md).

## 7. База данных

**Три таблицы.**

- `users` — пользователи: почта (уникальная, без учёта регистра), хеш пароля, дата создания.
- `links` — ссылки: код (уникальный), оригинальный адрес, владелец, срок жизни, лимит переходов,
  счётчик лимита, признак активности.
- `click_events` — журнал переходов: номер ссылки, время, хеш IP, user-agent, referrer.

Связи: пользователь владеет многими ссылками, ссылка имеет много кликов. Владелец у ссылки может
быть пустым — колонку добавили миграцией позже, и у старых ссылок владельца нет.

**Номер ссылки — из последовательности, не автоинкремент таблицы.** `link_seq` стартует со 100000.
Из номера делается код, поэтому номер нужен до вставки.

**Индексы.** Уникальный по коду ссылки (страховка для алиасов), уникальный по почте в нижнем
регистре, по владельцу ссылки, и составной по `(номер ссылки, время)` в журнале кликов — он
поддерживает статистику.

**Мягкое удаление.** Удаление ссылки — это не `DELETE`, а установка признака «неактивна». Строка и
клики остаются, статистика и номер не ломаются. Переход по такой ссылке даёт 410. Кэш при этом
сбрасывается.

**Состояние ссылки не хранится отдельным полем.** «Жива/просрочена/исчерпана/удалена» выводится из
признака активности, срока и счётчика в момент чтения. Отдельной колонки «статус» нет.

**Миграции.** Flyway, четыре версии: V1 — ссылки и последовательность, V2 — пользователи, V3 —
владелец/срок/лимит, V4 — журнал кликов. Схема накатывается при старте, вручную ничего создавать не
надо.

Схема: [diagrams/08-er-schema.md](diagrams/08-er-schema.md).

## 8. Авторизация

**Что делает.** Регистрация и вход, выдача токена, проверка токена на защищённых запросах.

**Токен — JWT.** Это подписанная строка, внутри которой лежат номер пользователя, почта, время
выдачи и время окончания. Подпись — алгоритмом HS256 (симметричный ключ, один секрет на сервере).
Сервер проверяет подпись и срок **без обращения к базе** — поэтому авторизация «без состояния»
(stateless): сервер не хранит сессии, вся информация в самом токене.

- **Подвох, который надо признать.** Раз сессий нет, токен **нельзя отозвать** на сервере до истечения
  срока. Украденный токен работает, пока не протухнет. Срок — 1 час. Это осознанный обмен на
  простоту: не нужны хранилище сессий и эндпоинт отзыва.

**Пароли — BCrypt.** В базе лежит не пароль, а его хеш (BCrypt — алгоритм, который считается
намеренно медленно, чтобы перебор был дорогим). При входе пароль сравнивается с хешем.

**Регистрация и вход.** Только два эндпоинта: `register` (создаёт пользователя, 201 без тела) и
`login` (проверяет пароль, отдаёт токен). Refresh-токена и серверного выхода нет.

- **Почему нет refresh и logout?** Спека их не требует. Интерфейс компенсирует честно: токен живёт
  час, потом единый обработчик ошибки 401 сбрасывает его и уводит на экран входа с пометкой «сессия
  истекла». «Выход» очищает токен только в браузере. Цена — повторный вход каждый час и невозможность
  отозвать токен на сервере. Для учебного проекта это приемлемо.

**Неверные данные не различают «нет пользователя» и «не тот пароль».** Оба случая — одна ошибка 401.
Это чтобы нельзя было перебором узнать, какие почты зарегистрированы.

**Где проверяется владелец.** Не в фильтре безопасности, а в сервисе: метод проверяет, что ссылка
принадлежит текущему пользователю, иначе 403. Фильтр только проверяет токен и пускает на `/api/**`.

**Что открыто без токена.** Переход по короткой ссылке, регистрация/вход, Swagger, метрики
Prometheus (но наружу их закрывает шлюз). Всё остальное под `/api/**` — с токеном.

Чем проверено: `AuthServiceTest`, `TokenServiceTest`, `AuthIT`, API-автотесты. Схема:
[diagrams/09-auth-session.md](diagrams/09-auth-session.md).

## 9. Шлюз и доставка интерфейса

**Что делает.** nginx — единственная точка входа. Отдаёт статику интерфейса и проксирует API в
приложение. Порт самого приложения наружу не проброшен.

**Почему интерфейс под `/app/`, а не в корне.** Корень уже занят публичным редиректом `GET /код`:
любой код ссылки конфликтовал бы с маршрутами интерфейса. Код `login` или `links` перестал бы
работать как ссылка, а интерфейс перехватывал бы клики. Поэтому:

- `/` → редирект на `/app/`;
- `/app/` — отдельное пространство имён интерфейса;
- всё остальное (включая `GET /код` и `/api/**`) → в приложение.

Чтобы ссылка не перекрыла отдачу интерфейса, коды `app` и `assets` зарезервированы: алиас `app`
создал бы ссылку `host/app`, и маршрут интерфейса перекрыл бы ей редирект — человек увидел бы
интерфейс вместо перехода.

**Кэш статики.** Файлы с хешем в имени (JS/CSS) отдаются с заголовком «кэшировать год, не менять»
(immutable) — их имя меняется при каждой сборке, поэтому кэш безопасен. А `index.html` — «не
кэшировать» (no-store), чтобы клиент всегда получал свежую оболочку с новыми ссылками на файлы.

**Почему бандл в образе шлюза, а не отдельный контейнер или CDN.** Один вход, один адрес (origin):
шлюз отдаёт и статику, и API, поэтому CORS не нужен и безопасность сервиса не тронута. Отдельный
контейнер — второй адрес и правила CORS. CDN — внешняя зависимость, а цель проекта «клон поднялся и
прошёл smoke»: свежему клону нужен только Docker. Цена — пересборка образа шлюза при правках
интерфейса; для разработки это смягчается dev-режимом.

**Сборка образа.** Двухэтапная: сначала Node собирает интерфейс (`npm ci` → `vite build`), потом
nginx забирает готовую статику и конфиг. В финальном образе Node нет — только nginx и файлы.

**Проброс адресов.** Шлюз передаёт `X-Forwarded-For/Proto/Port`, сервис их учитывает. Без этого все
клики писались бы с одним внутренним IP прокси, а Swagger терял бы правильный порт.

Чем проверено: e2e Playwright против поднятого стека, ручная проверка маршрутов. Схема:
[diagrams/10-web-delivery.md](diagrams/10-web-delivery.md).

## 10. Интерфейс (React)

**Что делает.** SPA (одностраничное приложение): вход/регистрация, список ссылок, создание, карточка
ссылки со статистикой, экран 404.

**Маршрутизация.** React Router, базовый путь `/app/`. Защищённые страницы обёрнуты в компонент,
который без токена уводит на вход.

**Клиент API.** Свой тонкий слой на `fetch` (без axios и подобных библиотек): таймаут 10 секунд,
подстановка токена в заголовок, разбор ошибок. Ошибка 401 где угодно → сброс токена и уход на вход.
Ошибки сервера разбираются по полям формы (например, «алиас занят» подсвечивает поле алиаса).

**Почему такие строгие зависимости.** В рантайме только `react`, `react-dom`, `react-router-dom`.
Без UI-китов, без библиотек графиков, без стейт-менеджеров. Это осознанно: меньше зависимостей —
меньше поверхность атаки и проще сборка. Статистику рисуем сами, без чарт-библиотеки.

**Валидация — зеркало серверной.** Клиент проверяет те же правила, что и сервер (длина адреса,
формат алиаса, резерв, срок в будущем, лимит целым). Числа и регулярки совпадают с серверными.
Занятость алиаса клиент проверить не может — это остаётся за серверным 409.

**Два языка.** RU и EN из одного словаря: в коде только ключи, тексты в одном месте. Переключение
языка не требует правок компонентов.

**Токен — в sessionStorage, не в localStorage.** Умирает вместе с вкладкой и не расшаривается между
вкладками. Это честнее для «выхода»: закрыл вкладку — токена нет.

**Покрытие.** Для API-слоя и библиотек — 100 % строк, для остального — 80 % строк / 75 % веток.
Гейт покрытия в CI не даёт уронить планку.

Чем проверено: Vitest (юнит), Playwright (e2e в реальном браузере). Подробнее — [web.md](web.md).

## 11. Метрики и мониторинг

**Что делает.** Сервис отдаёт метрики, Prometheus их собирает, Grafana рисует дашборд на 10 панелей.

**Как снято.** Эндпоинт `/actuator/prometheus` на сервисе открыт без токена (упрощение учебного
проекта). Но **наружу через шлюз он закрыт** (403) — Prometheus ходит к сервису напрямую внутри сети
Docker. То есть метрики доступны мониторингу, но не торчат в интернет.

**Что меряем.** Время ответов по эндпоинтам (гистограмма, чтобы считать перцентили), попадания/промахи/
ошибки кэша, ошибки публикации кликов, состояние пула соединений с базой, память и сборщик мусора
JVM, долг обработчика Kafka, загрузка процессора.

**Дашборд.** 10 панелей: частота и ошибки редиректа, перцентили редиректа, ошибки 5xx, создание
ссылок, доля попаданий кэша, куча JVM, сборщик мусора, пул соединений, долг Kafka, CPU процесса.

**Почему это важно для рассказа.** Именно по метрикам найдено узкое место стенда (долг обработчика
Kafka) и дефект с индексом — не по догадкам, а по счётчикам. Метрики — не украшение, а инструмент
диагностики (раздел 14).

Схема: [diagrams/11-metrics.md](diagrams/11-metrics.md).

## 12. Тесты

Пирамида от быстрых к медленным:

**Юнит и интеграционные (сервис).** 104 юнит-теста + 19 интеграционных. Интеграционные поднимают
настоящие Postgres/Redis/Kafka в контейнерах (Testcontainers) — не моки. Покрытие строк — 100 %
(JaCoCo, гейт не даёт уронить). Это значит: каждая строка кода сервиса исполняется в тестах.

**API-автотесты.** 38 тестов на REST Assured (6 смоук + 32 регресс), чёрный ящик: только HTTP, без
доступа к базе и без Spring. Отчёты в Allure.

- **Как боролся с нестабильными тестами (флейками).** По причине, а не повторами (повторов в сьюте
  нет намеренно): (1) аналитика приходит из Kafka позже ответа — жду её через Awaitility с
  ограничением по времени, а не `sleep`; (2) каждый тест регистрирует своего пользователя и свои
  ссылки — тесты не делят состояние и их можно перемешивать; (3) лимит создания поднят в тестовом
  окружении, иначе сьют падал на одиннадцатом создании; (4) в CI стек поднимается и снимается внутри
  сборки — прогон не зависит от остатков предыдущего.

**Браузерные e2e.** 6 сценариев Playwright в реальном Chromium против поднятого стека: регистрация,
вход, создание, переход, статистика, лимит. Один воркер, без повторов.

**Нагрузка.** Gatling-симуляции: постоянная нагрузка, разгон до отказа, короткий пик, долгий прогон.
Ими сделаны эксперименты раздела 14.

**Мутационные проверки.** Чтобы доказать, что тест ловит именно нужный дефект, код специально
портят и смотрят, что тест падает. Так показано, что конкурентный тест ловит гонку лимита (раздел 5),
а проверка владельца ловит её отсутствие. Это сильнее, чем «тест зелёный».

Подробнее: [autotests.md](autotests.md), [test-validation.md](test-validation.md).

## 13. CI/CD

**Два контура.**

**GitHub Actions** — то, что проверяет сам GitHub на каждый пуш/PR: юнит и интеграционные тесты
сервиса, API-автотесты против стека (workflow поднимает его на раннере), контур интерфейса (линт,
типы, юнит с покрытием, затем e2e). Версии плагинов зафиксированы числами.

**Jenkins** — свой, поднимается тем же compose. Полный прогон: тесты сервиса → юнит-гейт интерфейса
(в контейнере, потому что Node на агенте нет) → сборка образов → свой стек на отдельных портах →
API-автотесты → e2e → отчёты в артефакты → снятие стека. Секреты генерируются на время сборки и в
репозиторий не попадают.

**Зачем два, если стек поднимается и там и там.** Раннер GitHub эфемерный: история сборок, артефакты
и постоянный docker-демон остаются за Jenkins. Плюс интеграционные тесты с Allure живут там.

**DooD (Docker-outside-of-Docker).** Jenkins обращается к docker-демону хоста через сокет, а не
поднимает свой демон внутри. Тонкость: демон не видит файлы рабочей папки сборки, поэтому контекст
сборки передаётся потоком, а конфиг nginx запекается в образ, а не монтируется.

**Реальный прогон.** Сборка Jenkins №6: успех за ~7 мин 41 с; сервис 104+19 тестов и покрытие
387/387 строк, интерфейс 179 тестов, API 38, Playwright 6. После — независимая проверка, что
тестовые контейнеры/тома удалены, а основная база и прежние образы целы.

Подробнее: [ci-jenkins.md](ci-jenkins.md).

## 14. Нагрузочные эксперименты (что выяснили)

Шесть экспериментов. У каждого гипотеза записана **до** прогонов, пороги зафиксированы заранее.
Часть гипотез не подтвердилась — и это оставлено как есть, а не переписано задним числом. Это важно
сказать на собесе: методика честная.

**Главный вывод всего стенда:** первое узкое место — **обработчик очереди Kafka**, а не HTTP и не
база. Долг обработчика растёт раньше, чем очередь за соединениями с базой. И это доказано
вмешательством, а не догадкой.

| № | Что сравнивали | Что выяснили (реальные цифры) |
|---|---|---|
| 7.1 | кэш Redis против без кэша | выигрыш только там, где сервис упирается в себя: на 1000 запросах/с p95 ниже в 3,1 раза, CPU 92 % против 159 %. На 200 запросах/с разницы нет (4 мс против 4 мс). Без кэша узкое место — очередь за соединением, а не процессор |
| 7.2 | размер пула соединений 5/10/20/50 | оптимум 20: очередь за соединениями исчезает. Выбран по механизму очереди, а не по кривой времени ответа — медианы стоят немонотонно, разброс внутри варианта больше разницы между ними |
| 7.3 | клики через Kafka против записи в запросе | p95 9 мс против 117 мс, p99 52 против 488 мс. Первая измеренная разница, где варианты реально различаются. Потерь нет ни там, ни там |
| 7.4 | аналитика с индексом и без | гипотеза «без индекса в 5 раз хуже» **не подтвердилась**: без индекса оказалось даже быстрее (p95 1127 против 1582 мс). Дефект найден вслепую по счётчикам планов запроса и `EXPLAIN`, до вскрытия файла миграции |
| 7.5 | разгон 50→2000 запросов/с | точка деградации 1074 запроса/с. Первое узкое место — долг обработчика Kafka. Поднял параллельность обработчика 1→3 — ошибки исчезли полностью (13 589 из 615 000 → 0). Отказ на верху серии — транспортный, а не сервисный (в логе шлюза нет 500/502/504) |
| 7.6 | долгий прогон 644 запроса/с, 15 минут | дно кучи растёт, но это **не утечка**: по образцам памяти 55,1 из 56,8 МиБ — приёмные буферы Kafka, рост совпадает с долгом обработчика (корреляция 0,975). При нулевом долге дно плоское |

**Про 7.4 отдельно (любимый вопрос).** Почему без индекса стало быстрее? Потому что индексный путь у
этого запроса однопоточный и сбрасывает промежуточные данные на диск, а последовательное сканирование
распараллелено. Гипотеза не подтвердилась ни в какую сторону — и это честно записано. Дефект (пропавший
индекс) найден по метрикам: сканирования по индексу упали до нуля, последовательные выросли, и
`EXPLAIN` показал переход с `Index Only Scan` на `Seq Scan` с временем 26 → 303 мс на одном запросе.

**Почему цифры нельзя сравнивать с чужими стендами.** Генератор нагрузки и весь стек живут на одной
машине: 4 ядра делят сервис, база, Redis, Kafka, мониторинг и сам Gatling; приложение ограничено
2 ядрами и 1 ГБ памяти. Поэтому абсолютные запросы/с и миллисекунды — свойство этого стенда.
Переносимы только отношения внутри одного прогона. Худший случай зафиксирован явно: серию, которая
должна была дать «потолок» числом, отбросили целиком — на высоких уровнях генератор сам перестаёт
быть нейтральным наблюдателем (показывал 111 с там, где сервис насчитал максимум 5,6 с).

Отчёты: [experiments/](experiments/) — по одному на эксперимент, с гипотезой, методикой и пересчётом
чисел из журналов.

## 15. Что честно не сделано (и что бы улучшил)

Это раздел, который спасает от блефа. На «а что бы улучшил» — отвечать отсюда, а не выдумывать.

- **Один узел, отказоустойчивости нет.** Одно приложение, одна база без реплик, один брокер Kafka,
  Redis не кластер. После падения кэша первые секунды — холодные промахи в базу на каждый запрос.
- **Лимит создания в памяти процесса.** При двух инстансах у каждого свой, при перезапуске
  обнуляется. Не защита от распределённого случая.
- **Коды предсказуемы, редирект не лимитирован.** Перебор кодов — открытая дверь. Лечится случайной
  частью кода и отдельным лимитом на редирект. Не сделано осознанно.
- **Аналитика по сырым событиям.** После долгого прогона в журнале 12,4 млн строк, и каждый запрос
  статистики агрегирует их на лету. Нужны предрасчитанные агрегаты или отдельная таблица-сводка.
- **Обработчик Kafka — узкое место, и оно не исправлено в коде.** Параллельность 3 убирает ошибки
  (проверено экспериментом), но в конфиге осталась 1. Улучшение проверено как эксперимент, а не
  заложено как дефолт. Следующий шаг — пакетная вставка в обработчике и замер, при какой нагрузке
  долг перестаёт расти.
- **Долгий прогон был 15 минут, а не 1–2 часа.** Вывод «узкое место не HTTP» переносим, а вывод «нет
  медленной утечки» на этом горизонте сделать нельзя.
- **Интерфейс не мерил нагрузкой.** Нагрузка измеряет HTTP-тракт сервиса, отрисовку в браузере никто
  не мерил.
- **Нет refresh-токена и серверного отзыва.** Токен нельзя отозвать до истечения часа.

## 16. Каверзные вопросы — короткие ответы

То, что спрашивают чаще всего. Ответ — одно-два предложения, чтобы не поплыть. Глубже —
[interview-notes.md](interview-notes.md).

**Почему код ссылки предсказуемый, это же дыра?**
Да, коды идут подряд и редирект публичный. Это осознанный обмен: номер из счётчика не даёт коллизий
и не требует цикла проверки. Частично закрывается алиасом, сроком и лимитом. Случайную часть и лимит
на редирект не делал — знаю про это.

**Что если Redis упадёт? А Kafka?**
Redis — редирект идёт через базу и остаётся 302, только медленнее; ошибка считается в метрику.
Kafka — редирект всё равно 302, событие теряется; ошибка считается в метрику (с задержкой ~2 мин).
Оба проверены тестами и руками.

**Как лимит переходов не перерасходуется при гонке?**
Один атомарный `UPDATE ... WHERE click_count < max_clicks`: ноль строк = исчерпан → 410. Гонку
разруливает база. Доказано мутацией: «прочитал-проверил-записал» даёт 14 переходов вместо 5.

**Почему статистика с задержкой?**
Клик пишется не в запросе, а фоновым обработчиком через Kafka. Редирект отдаётся сразу, запись
догоняет. Замерено: p95 9 мс против 117 мс при записи в запросе.

**Почему 302, а не 301?**
301 браузер кэширует навсегда — повторные клики не дошли бы до сервера, сломались бы счётчик, лимит
и срок. 302 каждый раз приходит на сервер.

**Почему интерфейс под /app/, а не в корне?**
Корень занят публичным редиректом `GET /код`. В корне код `login` конфликтовал бы с маршрутом
интерфейса. Поэтому интерфейс в отдельном пространстве `/app/`, а `app`/`assets` зарезервированы.

**Почему свой кэш, а не @Cacheable?**
Два ключа с разной ценой промаха и разным TTL, плюс нужен выключатель кэша для эксперимента.
У аннотации один ключ и один TTL на метод.

**Почему JWT без отзыва? Как живёте без logout?**
Токен stateless, сервер сессии не хранит — отозвать нельзя до истечения часа. Интерфейс на 401
сбрасывает токен и уводит на вход. «Выход» чистит токен в браузере. Осознанный обмен на простоту.

**Где узкое место стенда и как доказал?**
Обработчик Kafka: долг растёт раньше очереди за соединениями. Доказательство — вмешательство:
параллельность 1→3 убрала все ошибки (13 589 → 0) на том же разгоне.

**Почему без индекса стало быстрее, а не хуже?**
Индексный путь однопоточный и сбрасывает данные на диск, последовательный — распараллелен. Гипотеза
«х5 хуже» не подтвердилась ни в какую сторону, оставлено честно. Дефект найден по счётчикам планов
и `EXPLAIN`.

**Почему цифры нагрузки нельзя сравнивать с чужими?**
Генератор и стек на одной машине, 4 ядра на всех. Абсолютные числа — свойство стенда, переносимы
только отношения внутри прогона.

**Почему IP хешем?**
Приватность: в базе SHA-256 от «адрес + соль», уникальных посетителей посчитать можно, адрес
восстановить — нет.

**Почему бандл в образе шлюза?**
Один вход и один адрес — CORS не нужен, свежему клону нужен только Docker. Цена — пересборка образа
при правках интерфейса.

**Что бы улучшил в первую очередь?**
Пакетную вставку в обработчике Kafka и предрасчитанные агрегаты статистики — это два реальных узких
места. Дальше — случайная часть кода и лимит на редирект, распределённый лимит создания.

## 17. Шпаргалка: числа и факты, которые можно назвать

Всё проверено по коду и отчётам, не выдумано.

- Стек: Spring Boot (Java 21), PostgreSQL 16, Redis 7, Kafka 3.9.1, nginx 1.30.6, React 19 + Vite.
- Код ссылки: Base62 от последовательности `link_seq` (старт 100000), алфавит `0-9A-Za-z`.
- Алиас: `^[A-Za-z0-9_-]{3,32}$`; резерв: api, actuator, swagger-ui, v3, app, assets.
- Адрес: http/https, непустой хост, до 2048 символов.
- Токен: JWT HS256, срок 1 час, без отзыва; пароли BCrypt.
- Лимит создания: 10/мин на пользователя по умолчанию, в памяти, 429 + Retry-After.
- Кэш: два ключа (`link:код`, `link-id:код`), MGET, TTL = min(настроенный, до конца срока); ссылки с
  лимитом не кэшируются; таймаут Redis 200 мс.
- Kafka: топик `click-events`, 3 партиции / 1 реплика, ключ = номер ссылки, `max.block.ms` 500,
  группа `click-writer`, дедупликации нет.
- Лимит переходов: атомарный `UPDATE`, 0 строк → 410; безлимитные строку не трогают.
- Редирект: 302 (не 301); 404 — код неизвестен; 410 — удалена/просрочена/исчерпана.
- IP: SHA-256(адрес + соль), в базе хеш.
- Шлюз: единый вход, `/app/` статика, `/actuator/prometheus` наружу закрыт, тело до 16 КБ, таймауты
  прокси 2 с / 10 с.
- Метрики: Prometheus снимает каждые 5 с напрямую с сервиса, Grafana — 10 панелей.
- Тесты: сервис 104 юнит + 19 интеграционных, покрытие 387/387 строк (100 %); интерфейс 179 тестов
  (33 файла); API 38 (6 смоук + 32 регресс); Playwright 6; нагрузка Gatling.
- Покрытие интерфейса: API-слой и библиотеки 100 % строк, остальное 80 % строк / 75 % веток.
- Эксперименты: кэш p95 ниже в 3,1 раза на 1000 запросах/с; пул оптимум 20; клики p95 9 против
  117 мс; точка деградации 1074 запроса/с; параллельность 3 → ошибки 13 589 → 0; долгий прогон
  644 запроса/с 15 мин, рост кучи — буферы Kafka (корреляция с долгом 0,975).
- Стенд: 4 ядра VM на всё, приложение 2 ядра / 1 ГБ; цифры стендовые.
- CI: GitHub Actions + Jenkins; сборка №6 — успех за ~7 мин 41 с.
